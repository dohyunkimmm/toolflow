## 공통 시연 전제와 판정 방식

1. `?review=1`에서 **Google SSO로 시작하기**를 누릅니다. 이는 가상 로그인입니다.
2. 각 시나리오는 가능하면 **체험 초기화 후 시작**합니다. 이전 요청·체크리스트가 브라우저 `sessionStorage`에 남아 있으면 결과 숫자가 달라집니다.
3. 직원 화면의 `신청현황`과 리뷰어의 `관리자 체험`은 **동일 브라우저에서 같은 직무를 선택했을 때의 가상 상태**를 공유합니다. 다른 직무는 별도로 상태를 유지합니다.
4. 표의 **관찰 기준**은 화면에서 확인할 항목입니다. **자동 검증 근거**는 실제 Playwright/Node 테스트가 다루는 범위이며, 사람이 별도로 관찰·평가한 성과를 의미하지 않습니다.
5. 해당 화면을 보이지 않게 숨기는 접근 제어는 **실제 인가가 아닙니다.** 사내 직원 개인정보·기밀·실제 계약 단가는 입력하지 않습니다.

## ① IT Support — 신청부터 처리 판단·이력까지

### 문제 정의

신규 구성원의 업무 도구 요청은 신청 내용, 처리 담당 역할, 승인 경로, 보완 요청, 처리 상태가 분산되면 누가 무엇을 확인했는지 추적하기 어렵습니다. ToolFlow에서는 **하나의 체험용 요청번호와 처리 이력에 신청·검토 정보를 연결**하는 방식을 보여줍니다.

**직무상 판단 질문:** 요청이 어떤 상태이고 누가 검토할 역할이며, 추가 확인·반려·재신청이 필요한가?

### 대표 흐름: Microsoft Office 요청

| 단계 | 사용자 조작 | 확인할 화면·판단 근거 |
| --- | --- | --- |
| 1. 요청 생성 | 경영지원·총무 직무 → **Microsoft Office** → **신청하기** → 신청 목적 확인·제출 | `ITSM-####` 형식의 **시연용** 요청번호, 신청현황의 **검토 대기** |
| 2. 검토 정보 입력 | **도움말 → IT 운영·기획 검토** → 해당 요청의 **요청 검토 기준·담당 부서** 펼치기 | 정책 버전·검토 경로·SLA 표시, 예외 확인 항목 |
| 3. 검토 근거 저장 | 우선순위 **우선**, 협의 담당부서 **GA팀**, 처리 담당 역할 **IT 라이선스 담당**, 판단 근거 **부서별 도구 중복 및 검토 필요** → **검토 정보 저장** | 입력값·처리 이력에 반영, 저장 후 버튼 키보드 초점 유지 |
| 4. 검토·지급 상태 전환 | 관리자 체험에서 **IT 검토 완료** → **지급 완료 처리** | **검토 대기 → 지급 대기 → 지급 완료** 상태 변화 |
| 5. 추적 확인 | 페이지 새로고침 → 신청현황 및 리뷰어 재진입 | 요청 상태·담당 역할·검토 근거와 완료 시각의 세션 복원 확인 |

**예외 경로:** 디자인 직무의 **Adobe Creative Cloud**는 승인 요청 항목입니다. 제품·플랜/기간 정보를 확인한 뒤 관리자 측 **반려 → 사유 확인 → 수정 후 재신청 → 관리자 승인하기**를 시연할 수 있습니다. 직무 외 도구·고권한·비용 부담 부서 미확인 사례는 **정책상 추가 확인 안내**를 보여줍니다.

**판단·결과 해석:** 요청 우선순위·협의 부서·담당 역할은 **검토용 값**입니다. 이를 저장해도 실제 담당자에게 티켓을 배정하거나 에스컬레이션 알림을 발송하지 않고, SLA 기한도 자동 변경되지 않습니다. 지급 완료는 **모의 상태**이며 실제 계정이나 SaaS 권한 발급을 뜻하지 않습니다.

**검증 근거:** `tests/onboard.spec.js` (동일 요청번호의 신청·IT 검토·지급 완료·복원, 반려·재신청), `tests/operations-planning.spec.js` (담당 역할·검토 사유·저장 후 초점·새로고침 복원), `scripts/tests/ops-planning.test.cjs` (허용된 담당 역할·정책 판단과 완료 시각 정합성).

**설명할 핵심 역량:** *요청 접수 → 검토 조건 확인 → 처리 이력 관리 → 예외 상황 추적*.

## ② IT기획 / ISP·PM — 라이선스 도입 대안과 IT 서비스 품질 판단

### 문제 정의

라이선스 도입 필요성은 신청 건수만으로 판단하기 어렵습니다. 직무별 정책, 신규·기존 좌석 활용 대안, 예산, 서비스 품질의 측정 가능성을 함께 봐야 합니다. ToolFlow는 **가정값을 분리한 비용 시나리오와 요청 품질 지표를 통해 의사결정 근거를 설명**합니다.

**직무상 판단 질문:** 현재 예산·수요 가정에서 어떤 대안을 먼저 검토하고, 어떤 운영 지표를 개선 대상으로 삼을 것인가?

### 대표 흐름: 신규 구매 대 기존 좌석 활용 비교

1. 리뷰어 체험 로그인 → **도움말 → IT 운영·기획 검토** → **IT 운영 정책·예산·성과 검토 (시나리오)** 펼치기.
2. 예시 신규 좌석 **12개**, 예시 월 단가 **20,000원**, 기존 좌석 재활용 **2개**, 예시 월 예산 **250,000원**을 입력하고 **대안 비용 다시 계산**.
3. 다음 **가정 기반 계산**을 확인합니다.

| 비교 | 계산 | 예시 월 비용 |
| --- | --- | ---: |
| 신규 12좌석 도입 | 12 × 20,000원 | 240,000원 |
| 기존 2좌석 활용 | (12 - 2) × 20,000원 | 200,000원 |
| 모델상 비용 차이 | 240,000 - 200,000원 | **40,000원** |

4. 현재 모델은 **예산 이내·기존 좌석 활용 우선 검토**를 표시합니다. 이는 구매 승인이 아니라 **대안 검토 권고**입니다. 기존 좌석의 실제 이용 가능성과 계약·사용 현황 확인이 선행되어야 합니다.
5. **반대 조건**도 확인합니다. 10좌석 × 30,000원, 재활용 0개, 예산 100,000원을 입력하면 **예산 초과 · 대안 재검토**와 필요 좌석·기간·대체 도구 검토 안내가 표시됩니다.

### 보조 흐름: KPI를 개선 과제로 연결

- **전체 요청·완료·예외 요청·재신청 포함 요청**과 **기한 내 완료율**을 확인합니다.
- 기한 내 완료율의 분모는 **처리 기한과 완료 시각이 모두 있는 완료 요청**입니다. 측정 대상이 없다면 성과를 0%나 100%로 단정하지 않고 **산출 대상 없음/판정 보류**로 안내합니다.
- 시나리오의 **90%는 예시 목표**일 뿐 실제 조직 SLA 목표가 아닙니다. 목표 미달 시 기한 초과 사례 검토, 예외 요청 시 승인 기준 점검, 재신청 발생 시 신청 안내·입력값 개선을 **후보 과제**로 제시합니다.
- 실제 정책 변경 승인·투자 집행·ROI 실현·전사 로드맵 실행은 제공되지 않습니다. 화면 내 추진안은 **검토 순서 예시**입니다.

**검증 근거:** `scripts/tests/ops-planning.test.cjs` (예산 이내/초과·0좌석·비용 차이·KPI 분모·목표 해석), `tests/operations-planning.spec.js` (12/20,000/2/250,000 비용 비교, 10/30,000/0/100,000 예산 초과와 UI 권고).

**설명할 핵심 역량:** *IT 운영 현황·정책 분석 → 예산·비용 대안 비교 → KPI 해석 → 개선 과제 후보 선정*.

## ③ GA · 경영지원/인사총무 — 부서별 입사 준비와 라이선스 현황 구분

### 문제 정의

입사 준비 업무를 라이선스 신청 하나로 간주하면 장비·근무 공간·계정 안내·교육 등 다른 부서의 준비 상태를 놓치기 쉽습니다. ToolFlow는 **입사 단계별 준비 항목과 필수 라이선스 상태를 분리해 보여주고**, 직무를 바꾸더라도 각 체험 상태를 독립적으로 보관합니다.

**직무상 판단 질문:** 입사 전·입사일·입사 후 중 어떤 준비 항목을 어느 부서가 확인해야 하며, 라이선스 신청은 실제로 어느 단계에 있는가?

### 대표 흐름: 경영지원·총무 입사 준비

1. 리뷰어 체험 로그인 → **경영지원·총무** 직무 확인 → **도움말 → 입사 준비 체크리스트 · 부서별 시나리오** 펼치기.
2. 체크리스트 6개 항목과 담당 역할을 확인합니다.

| 시점 | 체험상 담당 | 확인 항목 |
| --- | --- | --- |
| 입사 전 | IT팀 | 업무 단말 준비 일정 확인 |
| 입사 전 | GA팀 | 근무 공간·출입 안내 확인 |
| 입사일 | IT팀 | 계정 접근·로그인 안내 확인 |
| 입사일 | IT팀 | 직무별 필수 라이선스 신청 현황 확인 |
| 입사 후 | HR팀 | 인사 서류·교육 안내 확인 |
| 입사 후 | GA팀 | 미완료 준비 항목 담당자 확인 |

3. **업무 단말 준비 일정 확인**을 체크하면 **준비 항목 1/6건 표시 완료**로 바뀝니다. 이는 실제 IT팀의 장비 준비 완료가 아닌 **시연용 체크 상태**입니다.
4. 별도로 표시되는 **필수 라이선스 준비 현황**을 확인합니다. 공통 기본 제공은 **제공 가정**, 신청이 완료된 라이선스는 **체험상 지급 완료**로 계산합니다. 체크리스트 항목을 선택한 것만으로 라이선스 발급 상태가 완료되지 않습니다.
5. 직무를 **디자인**으로 전환해 체크 상태가 구분되는지 확인한 뒤 **경영지원·총무**로 돌아와 저장된 선택 상태를 확인합니다. **체험 초기화** 시 체크 상태가 해제되는지도 확인합니다.

**업무 판단:** 미완료 준비 항목과 미완료 라이선스는 동일하지 않습니다. GA 관점에서는 시점별 담당 부서 확인·업무 인계에 활용할 절차를 보여주되, 각 부서에 자동으로 업무를 배정하거나 자산을 지급하지는 않습니다.

**검증 근거:** `tests/operations-planning.spec.js` (6개 체크리스트·체크 상태·직무 분리·세션 복원·초기화·필수 라이선스 안내), `scripts/tests/ops-planning.test.cjs` (필수 라이선스가 기본 제공 가정 또는 완료 요청일 때만 준비로 계산).

**설명할 핵심 역량:** *온보딩 업무 분류 → IT·GA·HR 협업 경계 정의 → 준비 상태·라이선스 현황 구분 → 인계 절차 표준화*.
